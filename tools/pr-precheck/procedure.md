## Read order

<!-- What gets read, in what order, before any check is graded, and
what to note down from each part while reading. A complete procedure
decides where the plan sits in the order (before the diff? before the
description?) and says why the order matters for the side-by-side
checks that come later. -->
Read the issue at hand first. Then read the plan to supplement the issue. Finally, read the pull request and its accompanying commits to see if they align with the rest of the gathered information.

## Evidence gathering

<!-- For each evidence family your rubric's checks name, the concrete

against plan scope, claimed evidence against the plan's test plan and

Read `references/evidence-guide.md` for instructions on how to gather said evidence. You will use this guidance when evaulating each check in `rubric.md`. When gathering repro-evidence in live-mode, look for comments made in the file `beat-1-sandbox/unit-2/reproduction.md`.

## Check execution

<!-- How one check runs against gathered evidence: in what order the
checks execute, what an executor does when evidence for a check is
genuinely absent, and when a check may be graded without re-reading
the whole package. A complete procedure makes two executors grade the
same package the same way. -->
Grade each check `pass`, `fail`, or `unclear`, with a one-line evidence quote or fact for each grade. If the wording of the check itself is unclear, give it an `unclear` grade, with the reasoning that you had to question what a check meant. Also give the check an `unclear` grade if the evidence needed is truly absent, and the pass condition does not specify which grade to give if evidence is absent.

## Verdict assembly

<!-- How the per-check grades become the final accept or reject:

Apply the rubric's verdict rule to produce the final verdict:
`accept` (ready to post) or `reject` (hold). No third verdict exists.
